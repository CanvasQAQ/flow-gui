# Real-machine bring-up checklist

Coding agents should begin with `ON_MACHINE_AGENT_GUIDE.md`, which maps each
site fact to the config/adapter and proof that may need to change. This checklist
is the acceptance sequence, not a license to edit the Workflow core.

## One-time installation

1. Create a Python 3.11+ virtual environment on a filesystem visible to the
   Backend host; install `flow-backend[parquet]`.
2. Install the private algorithm package into the same environment.
3. Copy `config/site.example.json` to a site-owned path and set
   `FLOWPILOT_SITE_CONFIG` to it.
4. Set `FLOWPILOT_DATA_DIR` to local durable storage and
   `FLOWPILOT_WORKSPACE_DIR` to the simulation filesystem.
5. Confirm Backend and LSF execution nodes can read the manifests, SP files and
   Runner executable and can write each Case directory.
6. Keep source datasets read-only to the application account.

## Confidential conformance fixtures

Create a small private fixture directory that never enters Git:

- one normal SP/MT pair;
- one SP with continuation-line `.param` statements;
- one MT with a failed measure;
- one missing-MT Corner;
- one representative waveform input and the MT file generated by Postprocess;
- one public Parquet snapshot containing normal Job and Array rows;
- sanitized `bsub` success and failure receipts.

Tests on that machine must assert only field names, counts and classifications;
they should not print netlist contents or measured values to CI logs.

## Dry-run acceptance

1. Start with `lsf.dryRun=true`.
2. Call `/api/v1/integration-checks` and resolve every `error` or `pending` item.
   Inspect the items themselves; the current top-level `ready` field is not a
   hard submission gate.
3. Scan the private fixture using append mode; verify valid/invalid counts.
4. Run overwrite mode twice; the second run must create no new input version.
5. Render one Testcase; diff only the expected `.PARAM` assignments.
6. Inspect the generated immutable Batch JSON and calculated `bsub` argument list.
7. Run `flow-batch-runner manifest.json --index 1` interactively in the same
   environment used by compute nodes.
8. Confirm Status identity, simulator exit code, expected outputs and logs.
9. Validate one Parquet snapshot and state transition for PEND, RUN, DONE, EXIT,
   missing and UNKNOWN evidence.
10. Run Postprocess, locate its generated MT, and validate all four phase Loss
    values through the configured HSPICE MT parser.

## Limited live acceptance

1. Set `dryRun=false` only for a dedicated test Queue/project.
2. Submit one normal Job and verify the receipt is persisted.
3. Submit a two-element Array and verify indices map to the intended Case paths.
4. Stop the Backend during PEND/RUN and verify restart recovery does not resubmit.
5. Stop it immediately after `bsub`; the Batch must become `status_unknown` until
   the public snapshot or manual evidence identifies it.
6. Force one Element failure; confirm no automatic retry occurs.
7. Preview and confirm a one-Element resubmit; verify a new Attempt and Batch use
   the same Case directory.
8. Confirm pause blocks new decisions/submissions but continues observation and
   eligible Postprocess.
9. Preview `flow-admin rollback`; execute only after all downstream Jobs are
   terminal and verify old history remains visible.

## Production gate

- Database and immutable snapshots are backed up or reside on protected storage.
- Directory permissions match the compute-node account/group design.
- No telemetry, uploaded diagnostics, or external network dependency is enabled.
- Logs contain IDs, paths and state evidence but no SP/MT file contents.
- LSF Queue/resource defaults and maximum Array size are reviewed by the site
  administrator.
- Snapshot retention is longer than the expected Backend outage window, or an
  approved manual diagnostic procedure exists.
- Postprocess concurrency is set from measured filesystem/CPU cost.
- Electron starts Backend, waits for health, reports integration failures and
  terminates only the child process it started.
- If algorithm-specific Results charts are part of the release, the versioned
  presentation contract, result-detail API, allow-listed frontend renderer, and
  sanitized contract tests described in `INTEGRATION_CONTRACTS.md` are complete;
  the current synthetic chart data is not accepted for production.
- Real SP/MT names are supplied only by the external site config/private
  package, while generic Backend/frontend code uses logical keys and descriptor
  labels according to `ALGORITHM_PRESENTATION_CONTRACT.md`; a search for the
  development aliases finds no production dependency.
