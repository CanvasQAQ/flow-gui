# 整体流程

> 状态：讨论稿
>
> 目的：先用容易理解的语言说明系统要完成什么，以及一次完整仿真流程如何运行。这里暂不规定具体代码写法和数据库字段。

## 1. 项目要解决的问题

这是一个围绕 LSF 仿真流程运行的本地桌面应用。

用户提供原始仿真模板并配置运行条件后，系统负责：

1. 根据当前 Stage 的规则生成一批候选参数；
2. 为每个候选参数准备仿真文件；
3. 通过用户电脑上的 LSF 命令提交仿真；
4. 持续查询仿真任务的运行状态；
5. 仿真完成后运行后处理脚本；
6. 把后处理结果整理成统一格式；
7. 把结果交给当前 Stage 的算法判断；
8. 根据算法判断补充更多仿真，或者进入下一个 Stage；
9. 按算法定义进入最终 Stage，并运行算法给出的完整参数；
10. 保存整个过程，供查看、恢复和复查。

## 2. 系统由哪些部分组成

### 桌面界面

Electron 和 React 负责用户直接看到和操作的部分，例如：

- 配置 PVT 条件；
- 创建一次新的完整流程；
- 查看 Stage、候选方案、任务和结果；
- 执行暂停、继续和人工重试；
- 查看日志、曲线和其他结果文件。

界面只显示 Backend 提供的真实状态，不自己判断流程已经运行到哪一步。

### Electron 主进程

Electron 主进程只负责桌面应用自身的能力，例如：

- 创建和关闭窗口；
- 启动和关闭本地 Python Backend；
- 打开文件选择窗口；
- 提供必要的桌面系统能力。

它不负责 LSF 调度，也不决定 Workflow 的下一步。

### Python Backend

Python Backend 是流程的统一控制端，负责：

- 保存流程状态；
- 判断下一步应该做什么；
- 准备仿真工作目录；
- 调用 LSF 命令；
- 执行后处理；
- 调用 Stage 算法；
- 处理暂停、重试、回退和程序重启后的恢复；
- 向桌面界面提供状态和结果。

项目只运行一个本地 Python Backend。Backend 内部可以按职责分成多个模块，但暂时不拆成多个独立服务。

### SQLite

SQLite 保存流程中不能丢失的信息，例如：

- 当前运行到了哪个 Stage；
- 已经生成了哪些候选方案；
- 哪些任务已经提交；
- LSF Job ID；
- 每次执行的状态；
- 算法使用的输入和做出的决定；
- 错误信息和时间记录。

较大的文件不放进 SQLite，仍然保存在工作目录中，例如：

- SP 文件；
- 仿真输出；
- 波形；
- 日志；
- CSV；
- 图片；
- 原始后处理结果。

SQLite 只记录这些文件的位置和必要说明。

### LSF

Backend 通过用户电脑上已有的命令与 LSF 交互：

```text
bsub   提交任务
bjobs  直接查询任务（只作为非常规诊断手段）
bkill  终止任务
```

正常状态检查优先读取 IT 提供的公共 `bjobs.parquet` 快照。该快照约每 5 分钟更新一次，可以通过 DuckDB 自由查询。Backend 读取新快照后把与本项目有关的状态保存到 SQLite，不依赖公共快照永久保留历史。

本项目不替代 LSF 的集群调度功能，只负责决定提交什么、何时提交，以及如何记录和使用运行结果。

## 3. 一次完整流程中的对象

建议先使用下面这些容易区分的概念：

```text
初始化数据
├── 基础文件夹
├── 300～3000 个 Corner
└── 每个 Corner 的初始 Code 和参考结果

一次完整流程（Run，一组 PVT 条件）
├── 选中的 Corner A（独立推进）
│   ├── Stage 1
│   │   ├── 算法调用 #1 生成的 Testcase
│   │   ├── 算法判断：继续补 Code
│   │   ├── 算法调用 #2 生成的 Testcase
│   │   └── ...
│   └── 后续 Stage
├── 选中的 Corner B（独立推进）
│   └── ...
└── 算法方案定义的最终 Stage

一个 Testcase：普通 LSF Job
多个 Testcase：组合为 LSF Array Job
        ↓
一次 bsub 提交记为一个 Batch

注意：LSF Array Job 只是提交和执行方式，不决定某次算法生成的 Testcase 是否已经全部完成。
```

### 一次完整流程（Run）

表示用户启动的一次完整自动仿真过程。

它包含：

- 使用的初始化数据；
- 用户设置的一组 PVT 条件；
- 创建时选择以及后来补充的 Corner；
- Stage 和算法配置；
- 所有运行记录；
- 最终选出的参数；
- 最终 Stage 的结果。

同一份初始化数据可以创建多个 Run。每个 Run 只使用一组 PVT 条件，并且该 Run 下创建时选择和后来补充的所有 Corner 都使用这组 PVT 条件。当前 PVT 配置项是 VDD 和 VCM。

Run 创建后仍可继续补充 Corner。每个 Corner 加入 Run 时固定自己使用的原始 SP、初始 Code 和输入版本；以后扫描基础目录不会让它在运行中静默换用新输入。

Run 下的每个 Corner 都像一个独立的 Monte Carlo 采样点：各自调用当前 Stage 对应的算法，各自反复产生少量 Testcase、进入下一 Stage 并最终完成。一个 Corner 不等待其他 Corner。

### Stage 规则

Stage 规则描述一个业务阶段应该怎么运行，例如：

- 这个阶段允许修改哪些参数；
- 第一批候选方案如何产生；
- 仿真结果是否已经足够；
- 什么时候需要补充候选方案；
- 什么时候可以进入下一 Stage；
- 传给下一 Stage 的结果是什么。

Stage 规则本身不是一次运行记录。

### Stage 执行记录

表示某个 Stage 的一次实际运行。

需要单独保留执行记录，是因为 Rollback 后，算法可能再次进入一个历史上已经运行过的 Stage。例如：

```text
Stage 3 执行记录 #1

用户回到 Stage 2 的算法决策点重新决策

新决定再次进入 Stage 3，创建 Stage 3 执行记录 #2
```

第二次执行不会覆盖第一次执行。旧记录会保留，以便以后复查。

### 算法多次补点

一个 Stage 可能无法通过第一批仿真得到结论，因此需要分多轮增加候选方案。

```text
Stage 1
├── 第 1 轮：Code 30、31、32
├── 算法判断：结果还不够
├── 第 2 轮：Code 33、34
└── 算法判断：可以进入下一 Stage
```

这里的“一轮”表示一次算法判断之前新增加的一批仿真。

“轮次”主要用于界面展示和用户理解，不作为必须独立保存的业务对象。数据库保存每次算法调用的顺序以及它生成的 Testcase；界面可以据此显示第几轮。

### 候选方案

候选方案在 Stage 1 中也称为 Testcase，表示算法要求验证的一组具体仿真参数。

当前 Stage 1 的一组 Code 包含 9 个变量：

```text
1 个 rangesel
4 个 vrefsel
4 个 legsel
```

流程系统把这些 Code 当作算法提供的参数，不负责理解某个 Code 的电路意义或数值关系。

算法提出 Testcase 时提供该 Testcase 所需的完整 Code / Mode 参数集合。Workflow 不继承上一 Testcase 的参数，也不负责合并前面 Stage 的 Code，只负责验证基本格式并替换到原始 SP。

Corner 和 PVT 条件不属于这 9 个 Code。Corner 决定使用哪份原始 SP；PVT 条件属于整个 Run，并应用到该 Run 下的全部 Corner。

### 执行任务

候选方案需要通过仿真和后处理得到结果。当前至少包括：

- 仿真任务；
- 后处理任务。

以后如果实际流程需要，还可以增加其他任务类型。

逻辑任务与 LSF Job 不总是一对一。系统会把同一个 Corner 某次算法生成的多个 Testcase 组合成 LSF Array Job。例如算法一次生成 31 个 Testcase，可以提交一个含 31 个 Element 的 Array Job；如果只生成一个 Testcase，则提交普通 Job。

因此系统必须分别记录：

- 需要验证的逻辑 Testcase；
- Testcase 的某一次执行尝试；
- 该执行尝试被放入哪个 Batch；
- Batch 是普通 Job 还是 Array Job；
- 如果是 Array，它对应哪个 Element；
- 该次执行的独立状态和结果。

### 执行次数

同一个任务可能失败并重试。每一次真实执行都单独保存：

```text
仿真任务 A
├── 第 1 次执行：失败
├── 第 2 次执行：失败
└── 第 3 次执行：成功
```

Case 创建后拥有固定的网络侧结果目录。它保存最终 SP、成功回传的仿真波形、日志和 Postprocess 生成的 MT。计算节点实际执行时，推荐先把本次 Attempt 的输入复制到节点本地 `/SCRATCH`，在本地磁盘运行，再把输出安全回传到固定网络目录。

同一个 Testcase 重试或被用户重新提交时仍然对应原固定结果目录，但每次 Attempt 使用独立 Scratch 路径，避免两个执行在计算节点上写入同一目录。数据库会保留每次提交和执行尝试记录；网络侧旧波形、日志或 MT 的覆盖及保留策略仍需结合现场命名规则确定。

### 算法决定

算法得到结果后，需要明确记录它做出的决定。当前可以先分成：

- **补充仿真**：留在当前 Stage，创建下一轮候选方案；
- **进入下一 Stage**：当前 Stage 已得到需要的输出；
- **完成流程**：所有需要的 Stage 已完成；
- **无法继续**：算法判断当前流程不能正常得出结果。

除了决定本身，还需要保存：

- 算法读取了哪些结果；
- 算法名称；
- 算法配置；
- 新提出的候选方案或输出参数；
- 做出决定的原因；
- 做出决定的时间。

算法计算量很小，主要进行类似比较最大或最小 Eye Loss、选择对应 Code 的操作，应该在结果准备好后立即执行并反馈。每种算法方案可以定义不同数量和顺序的 Stage；用户选择算法方案后，也就选择了对应的 Stage 流程。具体 Stage 约定在以后编写相应算法时确定。

## 4. 流程如何向前运行

Backend 不应该从头到尾执行一个长函数，然后一直等待仿真结束。

它应该每次只做一个可以明确记录的小步骤：

```text
读取已经保存的状态
        ↓
检查 LSF 和工作目录中的真实情况
        ↓
判断当前可以进行哪一步
        ↓
只执行这一小步
        ↓
立即保存结果和新状态
        ↓
本次处理结束，等待下一次检查
```

可能的小步骤包括：

- 创建第一轮候选方案；
- 为候选方案准备文件；
- 提交一个已经准备好的仿真任务；
- 查询一批 LSF Job；
- 记录某个 Job 已经完成；
- 创建后处理任务；
- 执行一次本地后处理；
- 调用一次 Stage 算法；
- 根据算法决定创建下一轮仿真；
- 根据算法决定创建下一个 Stage。

每一步都必须允许安全地重复检查。重复检查不能导致：

- 同一个任务被重复提交；
- 同一批候选方案被重复创建；
- 下一个 Stage 被重复创建；
- 同一个算法决定被重复应用。

## 5. 两类后台检查

为了避免与 LSF 自身的“调度器”混淆，暂时使用下面两个名称。

### 流程推进器

流程推进器回答：

> 根据当前已经保存的状态，现在有哪些新工作可以开始？

例如：

- 为新候选方案准备文件；
- 提交已经准备好的任务；
- 在仿真成功后创建后处理任务；
- 在结果齐全后调用算法；
- 根据算法决定创建下一轮或下一个 Stage。

### 状态检查器

状态检查器回答：

> 数据库记录与 LSF、工作目录中的真实情况是否一致？

例如：

```text
数据库：Job 正在运行
LSF：Job 已经完成

处理：更新执行状态，并记录完成信息
```

或者：

```text
数据库：任务正在提交
实际情况：Backend 在提交过程中曾经崩溃

处理：先确认 LSF 是否已经收到任务，再决定恢复记录还是重新提交
```

系统可以在有新事件时立即检查，同时每隔一段时间进行一次周期检查。这样既能较快更新，也能在某次通知丢失后自行恢复。

## 6. 程序重启后如何继续

Python Backend 或 Electron 重启后，不能依靠重启前的内存状态。

Backend 重新启动后需要：

1. 从 SQLite 读取所有尚未结束的完整流程；
2. 找出正在准备、提交、排队、运行或后处理的任务；
3. 读取最新公共 LSF 状态快照，并结合状态文件和输出文件检查真实状态；
4. 检查约定位置上的结果文件和完成标记；
5. 修正数据库中已经过时的状态；
6. 继续执行当前能够安全进行的下一步。

恢复过程本身也必须允许重复执行。

## 7. 最需要小心的提交中断问题

下面这种情况必须专门设计恢复办法：

```text
Backend 执行 bsub
        ↓
LSF 已经接受 Job
        ↓
Backend 还没来得及保存 Job ID 就崩溃
        ↓
Backend 重启
```

此时如果 Backend 直接再次执行 `bsub`，同一个仿真可能被提交两次。

因此，任务在执行 `bsub` 之前就要先保存“正在提交”的记录，并且给这次提交设置一个可以在 LSF 中重新识别的唯一标记。重启后先根据这个标记查询 LSF：

- 如果已经找到对应 Job，就补写 Job ID 并继续跟踪；
- 如果能够确认 LSF 没有收到任务，才允许重新提交；
- 如果暂时无法确认，则进入“等待人工确认”或其他明确的异常状态，不能直接重复提交。

公共状态快照约有 5 分钟延迟，因此重启后不能因为第一份快照尚未找到唯一标记就立即重新提交。需要等待新快照，并在无法确认时保留“状态待确认”。

## 8. 文件和工作目录

用户提供的原始模板始终保持只读，不直接修改。

建议流程为：

```text
当前 Run Corner 引用的不可修改原始 SP 版本
   ↓
为 Case 建立固定工作目录
   ↓
从该输入版本的原始 SP 重新生成
   ↓
应用本 Run 的 PVT 条件
   ↓
应用当前 Stage 算法给出的 Code / Mode
   ↓
得到最终仿真输入
   ↓
执行仿真和后处理
```

现场已经确认每个 Testcase 的单个 SP 可以独立运行。LSF Runner 只把这个最终 SP 复制到计算节点 Scratch，不复制 Case 目录中的其他文件。

Case 的固定网络结果目录一旦创建，首次提交、失败重挂、状态未知后的人工重提以及已完成后的再次提交都对应这个逻辑目录；实际仿真工作目录是本次 Attempt 独占的计算节点 Scratch 目录。

两个 Attempt 可以同时拥有不同 Scratch 目录，但它们最终仍可能回传到同一个 Case 结果目录。回传必须核对当前有效 Attempt；过期 Attempt 不允许覆盖当前结果，应转存到隔离目录或标记待人工处理。

重新提交前不清理旧波形和 MT。新仿真先在独立 Scratch 和 Attempt 回传目录完成；Backend 确认它仍是当前有效 Attempt 后，才通过站点发布规则更新 Case 当前波形，新的批量 Postprocess 再更新 MT。Status 始终携带本次 Attempt 身份。

旧 MT 在新仿真和 Postprocess 完成前仍可能存在，因此“文件存在”不能表示当前执行已有有效结果。算法只能读取与当前有效执行匹配、并且已经完成本次 Postprocess 的结果记录。

## 9. 后处理

现有后处理脚本可能具有不同的参数和输出格式。Backend 不应把每个脚本的特殊逻辑散落在流程控制代码里。

每种后处理可以有自己的接入代码，但最后都转换成统一结果，例如：

```json
{
  "status": "success",
  "metrics": {
    "metric_a": 0.123,
    "metric_b": 45
  },
  "files": []
}
```

简单的后处理可以在本机运行。耗时较长或依赖集群环境的后处理，也可以作为 LSF 任务运行。具体采用哪种方式，应由任务配置决定。

## 10. 最终 Stage

最后一步也看作一种普通 Stage，使用与其他 Stage 相同的记录方式：

- Stage 执行记录；
- 候选方案；
- 仿真任务；
- 执行次数；
- 后处理结果；
- 最终判断。

最终 Stage 运行哪些 Code 仍由算法定义。Workflow 不负责把前面 Stage 的 Code 拼接成最终参数，也不假设前面 Stage 得到的值以后不能修改。

## 11. 暂停、重试和回退

### 暂停

当前暂定的默认含义是：

> 不再创建或提交新任务，但已经提交到 LSF 的任务继续运行，系统继续记录它们的状态和结果。

“暂停并取消等待中的 Job”以及“暂停并终止运行中的 Job”应该是另外的明确操作，不能与普通暂停混为一谈。

### 重试

重试针对某个失败或异常的执行任务。重试时：

- 原任务记录保留；
- 原执行记录保留在 SQLite；
- 新建一次执行记录；
- 新执行继续引用 Case 的固定网络目录，但使用新的 Scratch 和 Attempt 回传目录。

这里的“原执行记录保留”指 SQLite 中的提交、状态和时间历史。新旧 Attempt 的原始回传结果相互隔离；Backend 只发布当前有效 Attempt，网络侧历史结果的长期保留取决于清理策略。

失败、状态未知和 Postprocess 失败都不自动重试，统一等待用户通过筛选页面决定。`copyback_waiting` 单独处理：Recovery 同时提供“重新复制”和“放弃本次 Submit 并重新运行”。重新复制通过 LSF 子任务留下的 hostname 标记登录原节点；Backend 明确展示 SSH、源目录不存在或目标盘仍不可写等错误，不替用户判断 Scratch 是否已被站点清理。

- 忽略这个 Testcase，让它不再阻塞当前算法生成组；
- 或为它创建新的执行记录和新 Batch，重新仿真。

LSF Array 中只有部分 Element 失败时，不能把这次算法生成的全部 Testcase 重新提交。系统只应为失败或缺失结果的 Testcase 创建新的执行尝试，再将这些新尝试单独组合提交。

Postprocess 不以单个 Batch 完成为触发条件。只有某个 Corner、某个 Stage 中，最近一次算法生成的整组 Testcase 都达到结束条件，才触发批量 Postprocess。这组 Testcase 可能先后使用多个 Batch 才执行完成。

### Rollback

Rollback 是后端调试能力，不在前端 GUI 中提供。

调试时可以按 Run 和 Corner 列表或范围，一次将多个 Corner 回到指定 Stage 的算法决策点。目标决策以前已经完成的 Testcase、MT 和 Loss 继续复用；旧决定及后续路径标记为已被替代，然后直接使用当前后端中的算法代码重新做决定。

系统不管理或记录算法代码版本。用户自行确定哪些 Corner 需要重新决策。

某个 Corner 的受影响路径中如果还有 PEND、RUNNING、状态待确认或状态未知的 Job，则跳过该 Corner。用户先手动等待、删除或终止相关 LSF 任务，再重新执行批量 Rollback。

旧决定、旧 Stage、旧 Testcase 和文件全部保留，只有当前有效路径发生改变。当前不另外设计 Replay。

## 12. 性能方面先做什么

当前预计主要耗时来自：

- LSF 排队；
- 仿真运行；
- 后处理；
- 工作目录所在文件系统的读写。

因此暂时不需要拆分微服务，也不需要先引入 Redis、Celery、Kafka 或其他复杂组件。

优先考虑：

- 每份新的公共 `bjobs.parquet` 快照只读取一次，并一次筛选全部活跃 Job；
- 把快照中观察到的状态保存在本地 SQLite，防止公共数据清理后丢失历史；
- 一批状态更新放在同一个数据库事务中；
- 直接检查预先约定的结果路径，不反复递归扫描大目录；
- 正确使用普通 Job 和 Array Job，避免为每个 Testcase 都单独提交；
- 避免因为界面刷新而反复读取公共快照或执行 LSF 命令。
- 将仿真热路径放到计算节点本地 `/SCRATCH`，网络盘只承担输入分发、少量状态和最终结果回传；
- 将共享盘状态检查放入独立、可超时、可恢复的扫描执行器，不能阻塞 API 和其他 Workflow。

## 13. 当前共识

- 系统是本地桌面应用，使用 Electron、React 和本地 Python Backend；
- Python Backend 是流程状态和控制逻辑的唯一来源；
- 流程状态保存在 SQLite，不依赖内存维持；
- 大型仿真文件保存在工作目录，SQLite 记录路径和说明；
- 原始模板不直接修改；
- 每个 Case 创建后使用固定目录，后续所有执行继续使用该目录；
- 流程以可记录的小步骤向前推进；
- 重复检查不能造成重复提交或重复创建数据；
- 算法只负责提出候选方案和做决定，不直接操作 LSF、数据库或界面；
- 历史执行记录保留，不通过覆盖和删除来表示回退；
- 初始化数据默认只扫描一次，但用户可以主动重新扫描以发现新增文件或覆盖已有解析结果；
- 同一份初始化数据可以创建多个 Run；
- Run 创建后仍可分批补充 Corner；每个 Corner 加入时固定自己的输入版本；
- 一个 Run 只包含一组 PVT 条件，该 Run 下所有 Corner 使用相同 PVT 条件；
- 每个 Corner 独立反复调用算法、生成少量 Testcase 并得到自己的最终 Code；
- 每个 Corner 可以独立进入下一 Stage，不等待同一 Run 中的其他 Corner；
- 不同 Stage 可以使用不同的算法计算规则；
- 一个 Testcase 不等于一个 LSF Job，多个 Testcase 可以组成一个 LSF Array Job；
- Array 中部分仿真失败时不自动重挂；用户选择重新仿真后，只提交明确选择的部分；
- Postprocess 在单个 Corner 当前算法生成组的所有 Testcase 都已结束或被用户处理后执行，不以某个 Batch 或 Array 完成为触发条件；
- 本地批量 Postprocess 需要限制并发数量；
- 用户可以按 Corner、Stage、算法调用序号和状态筛选任意 Testcase，并重新提交明确选择的部分，包括已完成、失败、运行中或状态未知的 Case；
- Case 筛选只在当前 Run 内进行，Corner 支持 `1,2,3-5,6-20` 一类列表输入和反向排除；
- 每次提交使用 Setting 中当时有效的 LSF 配置，并把实际配置副本保存到 Batch；
- 普通暂停只停止创建和提交新任务，已提交任务继续运行并收集结果；取消等待任务和终止运行任务是另外的明确操作；
- 一个 Testcase 使用普通 LSF Job，多个 Testcase 使用 Array Job；
- LSF 内部如何排队和限制并发由 LSF 负责，不作为 Workflow 的业务逻辑；
- 后端提供可按 Corner 列表或范围批量执行的调试用 Rollback；不暴露到前端 GUI，也不管理算法版本；
- 暂时不引入微服务和外部任务队列。

## 14. 后续讨论入口

重新扫描、向已有 Run 补充 Corner 和 Rollback 的完整规则见《重新扫描、补充 Corner 与 Rollback》。当前没有阻塞主流程的未决问题；LSF 快照字段、文件命名、清单格式和算法接口等内容留到对应代码设计阶段确认。
