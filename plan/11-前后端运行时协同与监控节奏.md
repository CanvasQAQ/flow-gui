# 前后端运行时协同与监控节奏

## 当前结论（2026-08-23）

前后端基础运行时已经接通：UI 会读取 Backend 快照、订阅 SSE 并调用写操作；Electron 主进程会启动、健康检查、停止和重启 Backend。本地 mock 仍作为 Backend 不可用时的演示降级和部分图表/详情占位数据，不是生产事实源。

本文下面的内容同时包含“已实现的运行时合同”和“仍需收口的验收目标”。当前主要未完成项是：Dataset 大扫描仍为同步请求，算法专用 Results 图表尚无真实 API/数据合同，以及 LSF/HSPICE/共享盘的真机验收尚未完成。

Backend 是运行状态的唯一事实源。Frontend 不读取 SQLite、仿真目录、`status.json`、Parquet 或 LSF，也不自行推断 Stage 进度。

## Electron 管理 Backend

Electron 主进程负责启动自己安装目录中的 Backend，并公开启动、停止、重启、查看状态和打开日志目录五个受控操作。进程状态固定为：

`stopped -> starting -> ready -> degraded -> stopping -> stopped`，异常退出进入 `crashed`。

- 启动后每 250–500 ms 检查 `/api/v1/health`，就绪后降低到 5 s 心跳；
- Frontend 先显示“Backend 正在启动”，不等待 Backend 才创建窗口；
- 停止先进入 draining，拒绝新建 Run 和新提交 Batch；
- 正在执行的 `bsub` 最多等待 60 s；强制停止或进程崩溃时将 `submitting` 恢复为 `status_unknown`，绝不自动重提；
- Electron 只终止由自己启动且 PID/启动令牌匹配的子进程。

## UI 状态同步合同

首次打开页面用 REST 获取完整快照，之后使用 SSE 接收已提交事务产生的事件。每个事件包含单调递增的 `eventId` 和实体 `revision`；断线重连携带最后一个事件号。SSE 不可用时，Frontend 可以低成本拉取 Backend 数据库中的增量，但这种拉取不能触发共享盘或 DuckDB 扫描。

所有耗时操作立即返回 `202 + operationId`，不得让一次 HTTP 请求等待 Dataset 扫描、`bsub`、仿真或 Postprocess。UI 刷新只读 Backend，不触发扫盘或 DuckDB 查询。

Backend 为每个 Stage 返回明确的子步骤，不允许 Frontend 根据 Corner 的粗粒度状态猜测：

1. `algorithm_decision`
2. `prepare_cases`
3. `submit_batch`
4. `simulate_group`
5. `recovery_gate`
6. `postprocess`

每个子步骤状态为 `waiting / ongoing / complete / attention / skipped`，并带开始时间、更新时间、摘要、完成数/总数和错误说明。`bsub` 调用期间 Batch 已持久化为 `submitting`，所以 UI 的 `submit_batch` 必须稳定显示 ongoing 和已用时间。

UI 不需要为每个 Corner 展示证据写入、Backend 观察和下次检查三个时间。主界面只提供一个 Run/系统级“后台状态检查”指示：`正常 / 检查中 / 延迟 / 异常`。用户主要据此判断 Backend 是否仍在工作，而不是阅读每个 Corner 的扫描时间。最近一次成功检查时间可以放在指示器的次要文字或详情中，不作为主要信息；单个 Corner 的详细证据仅在排错详情页按需展示。

## bsub 阻塞与防重复

正常 `bsub` 可能运行 20–30 s。提交必须在独立、有限并发的提交执行器中运行，不能占用 API、状态扫描或 Postprocess 执行器。现场默认并发 1，可在验证 LSF 压力后提高到 2–4。

状态机为：

`ready -> submitting -> submitted`

明确的非零退出进入 `submit_failed`；超时、Backend 崩溃、成功输出无法解析等无法判断 LSF 是否已接收的情况进入 `status_unknown`。

- 只有数据库中 `ready` 到 `submitting` 的原子更新成功者可以调用一次 `bsub`；
- `submitting` 和 `status_unknown` 永远不自动调用 `bsub`；
- 默认提交超时 120 s，明显高于已知的 20–30 s；超时不等于失败；
- 每个 Batch 使用唯一 Job name，并在调用后落盘 receipt；
- 恢复时优先用唯一 Job name/receipt/Parquet 找回 Job ID，无法确认则保持 `status_unknown` 等待人工处理。

## 运行期扫盘与 DuckDB

运行期不递归扫描波形目录。默认状态文件仍位于各 Case 目录，数据库保存每个 Attempt 的精确路径，调度器只处理到期的活动 Attempt。改成 Batch 目录不会减少文件数和检查次数，只保留为真实机器 A/B 实验：

- 使用基于单调时钟/数据库 `nextCheckAt` 的定时任务，不再按 Workflow 空转次数触发；
- 每轮取 500–2000 个路径，按 `nextCheckAt` 分片；
- 先比较文件存在性、mtime 和 size，只有变化时才打开并解析 JSON；
- 所有已提交任务，无论尚未开始还是正在运行，默认约每 10 分钟检查一次；分片可以在这一窗口内均匀展开，避免第 10 分钟集中打盘；
- terminal Attempt 立即从轮询集合移除；
- 文件系统异常采用退避，不在每秒重复打日志。

状态文件由计算节点上的 Runner 更新：Backend 准备 Attempt 时写 `submit`；Job Element 真正启动时写 `staging_in`，本地输入准备好后写 `running`；仿真完成后写 `staging_out`；输出安全返回网络目录后写 `complete` 或 `failed`。每次都通过同目录临时文件加原子替换写入，只记录状态边界，不周期写 heartbeat。

HSPICE 已完成但网络结果盘爆满时使用独立的 `copyback_waiting` 状态。Frontend 在系统/Run 级提醒中显示“有结果复制失败”，Recovery 同时提供“重新复制”和“放弃本次 Submit 并重新运行”。Backend 每次都实际执行普通 SSH/复制命令并返回明确错误；项目不倒计时、不判断或管理站点已知的 24 小时 Scratch 清理机制。

Parquet 是辅助证据，不是 UI 查询源。它与状态文件使用相同的约 10 分钟协调周期；每轮先检查快照文件 identity（mtime + size），identity 未变化不启动 DuckDB。确认文件稳定或由原子 rename 发布后，才用一次 DuckDB 查询全部活跃 Job name。Backend 启动恢复、用户明确执行“立即刷新”可以额外触发一次受限协调，但页面普通刷新不能触发共享盘扫描。

## Dataset 扫描

Dataset 扫描仅由用户显式发起，不参与运行状态轮询。它应改为后台 operation：立即返回 `202`，持续报告发现、已解析、已跳过、失败和总数；每 50–200 个 Corner 分批提交数据库，并支持取消和失败后继续。append 模式跳过已有有效 Corner；overwrite 仅在 SP/MT 指纹变化时创建新版本。

## 验收要求

- 人工让 `bsub` 阻塞 30 s：页面仍可导航，Submit Batch 显示 ongoing，且只产生一个 receipt；
- 在 `submitting` 阶段杀死 Backend 并重启：不再次调用 `bsub`，页面显示 attention/status unknown；
- 断开 SSE 后恢复：事件不丢失、不倒退，页面最终与 REST 快照一致；
- 主界面用一个系统/Run 级指示器说明后台状态检查是否正常、正在进行、已经延迟或发生异常；普通页面刷新不增加扫盘次数；
- 模拟网络结果盘满：UI 提供重新复制和放弃旧 Submit 后重新运行；重新复制使用 LSF 子任务留下的 hostname，SSH/复制失败原因必须明确展示；
- 1 万、5 万和 10 万活动 Attempt 压测：记录单轮 stat 数、JSON 打开数、DuckDB 次数、CPU 和共享盘 IOPS，再确定现场分片和周期；
- Backend 启动失败、崩溃、停止和重启均有明确 UI 状态及可访问日志；
- Postprocess 只负责生成 MT；Backend 从每个 Case 的指定 MT 解析结果，不要求脚本输出 JSON。
