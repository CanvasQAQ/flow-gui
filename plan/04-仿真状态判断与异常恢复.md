# 仿真状态判断与异常恢复

> 状态：讨论稿
>
> 目的：解决 `status_*` 文件长期停在 Running、状态文件因磁盘满而消失、Backend 重启后无法确认任务真实状态，以及不能频繁执行 `bjobs` 等问题。

## 1. 当前做法

当前每个 LSF Array Element 通过状态文件表示执行进度：

```text
提交前：status_submit
LSF 开始执行 run.sh：status_running
仿真器正常结束：status_complete
仿真器异常结束：status_fail
```

`run.sh` 根据仿真器退出码决定最后写入 `complete` 还是 `fail`。

这套机制直观，也能避免 Backend 为了普通状态更新频繁查询 LSF，因此可以继续保留。对业务流程而言，只有当前执行对应的 `status_complete` 表示仿真成功；其他状态来源用于跟踪、发现异常和帮助用户判断，不能替代 `status_complete` 猜测成功。

## 2. 已经发现的失效情况

### 2.1 LSF 或执行节点异常终止任务

任务进入运行状态后，`run.sh` 已经写入 Running。随后任务被 LSF、执行节点故障或不可捕获信号终止，`run.sh` 没有机会执行最后的状态更新。

最终表现为：

```text
状态文件：一直是 Running
真实情况：仿真进程已经不存在
```

任何写在 `run.sh` 最后一步的逻辑都无法完全解决这种问题，因为脚本本身已经没有继续执行的机会。

### 2.2 磁盘空间或 Inode 耗尽

当前状态切换过程会先删除旧状态文件，再创建新状态文件。

当磁盘空间不足时：

```text
删除 status_running：成功
创建 status_fail：失败
```

最终目录中没有任何状态文件，Backend 无法知道任务曾经运行到哪里。

### 2.3 只根据文件无法区分的情况

下面几种情况在文件侧可能表现相同：

- 任务仍在运行，但长时间没有更新；
- 任务已经被 LSF 终止；
- 执行节点失联；
- 磁盘满导致状态更新失败；
- 状态文件被人工删除；
- 文件系统暂时不可访问。

所以“Running 文件很旧”不能直接等价为失败，“没有状态文件”也不能直接等价为重新提交。

## 3. 总体原则：成功看 Status，异常看多种证据

推荐把状态来源分成四层：

```text
1. Backend / SQLite
   系统打算提交什么、何时提交、属于哪个 Batch 和 Element

2. LSF
   Job 是否排队、运行、成功结束、异常结束或处于 UNKNOWN

3. run.sh 状态记录
   脚本是否启动、看到的仿真器退出码、最后一次成功写状态的时间

4. 实际输出
   波形是否存在且有效、Postprocess 是否成功、MT 是否完整
```

四层记录的职责不同：

- SQLite 是流程系统自己的持久记录；
- LSF 是 Job 是否仍然存在和如何结束的重要依据；
- 状态文件是计算节点主动留下的快速证据；
- 当前执行对应的 `status_complete` 是仿真成功的业务定义；
- 波形和 MT 由后续 Postprocess 检查，决定是否能得到算法需要的数据。

LSF DONE 不能把缺失或停在 Running 的 Status 自动改成成功；波形恰好存在也不能证明它属于当前执行。证据不完整或互相矛盾时，系统停下来等待用户决定。

## 4. 状态文件的改进

### 4.1 不再通过文件名表示唯一状态

推荐将多个互斥文件：

```text
status_submit
status_running
status_complete
status_fail
```

改成一个固定文件：

```text
status.json
```

内容示意：

```json
{
  "attempt_id": "attempt_123",
  "batch_id": "batch_45",
  "array_index": 7,
  "state": "RUNNING",
  "submitted_at": "...",
  "started_at": "...",
  "finished_at": null,
  "host": "...",
  "pid": 12345,
  "simulator_exit_code": null,
  "message": null
}
```

每次重新提交都会产生新的 `attempt_id`。Submit、Running、Complete 和 Fail 的每次更新都必须携带同一个 `attempt_id`。

Backend 只把与当前执行记录匹配的 Status 当作当前状态。固定目录中如果仍然存在旧执行写下的 Status 或 MT，不能直接当成本次执行结果。

状态切换时不能先删除旧文件。应按下面的顺序更新：

```text
把新内容写入同目录临时文件
        ↓
确认临时文件写入成功
        ↓
用 rename / mv 原子替换 status.json
```

如果磁盘满导致临时文件无法创建，旧的 `status.json` 仍然保留，不会变成完全没有状态。

如果暂时不改成 JSON，继续使用不同文件名，也必须先成功创建新状态文件，再删除旧状态文件，不能反过来。

重新提交前，Backend 先把 Status 更新为本次 `attempt_id` 对应的 Submit。只有写入成功，才允许该 Case 进入新的 LSF Batch。

### 4.2 状态文件只表示“最后一次成功留下的证据”

即使 `status.json` 内容是 RUNNING，也只表示：

> `run.sh` 曾经成功启动，并且最后一次成功写文件时仍在运行。

它不保证进程现在仍然存在。

同样，状态文件缺失表示“文件证据缺失”，不直接表示任务从未提交或必须重跑。

### 4.3 不建议高频写 Heartbeat

理论上可以让每个 Element 定期更新心跳，但在数万甚至十万级仿真下，大量计算节点持续写小文件会进一步增加共享文件系统压力。

第一版不建议为每个 Element 高频写 Heartbeat。可以只记录开始和结束事件，再通过低频 LSF 汇总查询处理长期 Running。

如果以后确实需要心跳，也应采用较长周期，并先评估共享文件系统负载。

## 5. run.sh 必须正确保留退出码

当前不依赖既有 `run.sh` 的具体实现，新版本按本节规则设计。

`run.sh` 需要单独保存仿真器退出码，不能因为最后一次状态写入命令成功而让整个 Job 错误地返回 0。

逻辑应该是：

```text
启动仿真器
        ↓
立即保存仿真器退出码
        ↓
根据仿真器退出码，尽力写入 Complete 或 Fail 状态
        ↓
根据仿真器和状态写入结果确定最终退出码
```

建议规则：

- 仿真器返回非零：LSF Job / Element 返回该错误，不允许被后续命令覆盖；
- 仿真器返回 0，但终态文件无法写入：返回流程系统约定的非零错误，让 LSF 留下 EXIT 证据；
- 仿真器成功并且 Complete 状态记录成功：返回 0。

仿真器原始退出码、输出检查结果和最终 Wrapper 退出码需要分开记录。具体错误码表以后设计，避免与 LSF 使用的信号退出码混淆。

可以使用退出处理逻辑尽量捕获普通错误和部分信号，但不能假设所有情况都能捕获。执行节点宕机或不可捕获信号仍然只能依靠 LSF 和 Backend 恢复。

## 6. 磁盘满的提前检查与降级

在启动仿真器前，`run.sh` 可以检查：

- 可用磁盘空间；
- 可用 Inode；
- 如果环境支持，用户或目录配额；
- 输出目录是否可写。

如果明显低于安全阈值，不启动仿真，直接以明确的非零退出码退出。

这只能减少磁盘满问题，不能完全保证运行过程中空间不会耗尽。

波形在计算节点 Scratch 生成时，Scratch 磁盘满可能阻止仿真或 stage-out；网络结果盘满则可能阻止最终回传。两者必须分别检查并记录。

网络结果盘满但 HSPICE 已成功时，状态记为 `copyback_waiting`，不能混同为仿真失败。只有实际运行的 LSF 子任务负责取得 hostname，并在 Case 网络目录创建同名零字节标记。Recovery 可以用普通 SSH 回到原节点，将 Scratch 文件夹全部内容重新复制到 Testcase 所在磁盘的 Attempt 回传目录。

项目不判断站点的 24 小时清理是否已经发生。重新复制失败时，Backend 明确返回 SSH、源目录不存在、目标不可写或复制失败等错误；用户可以再次尝试复制，或者明确放弃旧 Submit 并重新提交仿真。

默认继续在每个 Case 目录保存该 Attempt 的 `status.json`，由对应 LSF 子任务单独写入。如果现场另有与结果盘真正独立、容量受控的控制文件系统，可以考虑把 Status 放过去，让结果盘爆满时仍有机会记录 `staging_out` 或失败状态；这是可靠性隔离，不是确定的扫描性能优化。按 Batch 分片的目录布局只在真实机器 A/B 测试证明有效后启用。

无论是否有独立控制目录，Backend 都不能仅靠状态文件判断。

## 7. 使用 IT 提供的公共 LSF 状态快照

IT 在公用路径提供约每 5 分钟更新一次的 LSF 状态数据，其中包括 `bjobs.parquet`，可以使用 DuckDB 查询。

已知特点：

- 数据存在约 5 分钟更新延迟；
- 单次查询通常需要 4～5 秒；
- 可以自由查询，不会像频繁执行 `bjobs` 一样直接增加 LSF 负载；
- Job 完成一段时间后可能从快照中消失；
- `bhist` 查询单个 Job 可能需要 20～30 秒甚至卡住，不适合作为自动恢复手段。

因此正常流程不直接轮询 `bjobs`，也不自动循环调用 `bhist`。

### 7.1 只在公共快照更新后读取一次

Backend 可以先检查快照文件的更新时间、版本号或快照内的生成时间。只有确认出现新快照时，才执行一次 DuckDB 查询。

```text
公共快照没有更新
→ 不执行 DuckDB 查询

发现一份新快照
→ 一次查询本项目所有未结束的 Job / Array
→ 把查询结果保存到 SQLite
```

这样查询频率跟随公共数据的实际更新频率，不需要每隔几秒重复执行一个耗时 4～5 秒、结果又没有变化的查询。

UI 刷新只读取 SQLite，不能直接触发 DuckDB 查询。

### 7.2 每次观察结果都保存到 SQLite

公共 `bjobs.parquet` 是当前状态快照，不是本项目的永久历史库。

Backend 每次读到与本项目有关的数据后，都要保存：

- 公共快照的生成时间或文件更新时间；
- 本次读取时间；
- LSF Job ID 和 Array Index；
- 本次看到的状态；
- 退出码、执行主机和其他快照实际提供的字段；
- 这是第几份连续快照中的观察结果。

即使 Job 后来从公共快照消失，本项目仍然保留此前已经看到的 PEND、RUN、DONE 或 EXIT 记录。

### 7.3 缺失不等于失败

某个 Job 没出现在最新快照中，可能表示：

- `bsub` 刚完成，公共快照还没更新；
- Job 已经结束并在一段时间后被清理；
- 快照生成或读取暂时异常；
- Job ID 或名称匹配方式不正确；
- Job 的真实状态确实异常。

因此单次快照缺失不能触发自动重提。

建议至少检查：

```text
快照本身是否是新的
+ Job 在之前快照中的最后状态
+ status.json 最后证据
+ 波形和其他输出是否存在
+ 是否已经连续多份新快照缺失
```

确认公共快照更新时间非常重要。如果整个快照已经停止更新，不能把其中所有 Job 都误判成停滞。

### 7.4 直接命令只保留为非常规诊断

`bjobs` 不进入正常检查循环。以后如果 IT 允许，可以只在极少数“状态待确认”场景中由用户主动触发一次直接查询。

`bhist` 因单次查询就可能耗时 20～30 秒或卡住，不进入自动恢复路径。即使保留人工诊断入口，也需要明确超时，不能阻塞整个 Backend。

### 7.5 无法通过软件消除的恢复空白

下面的组合目前没有可靠证据可以自动判断：

```text
Backend 关闭或电脑重启较长时间
+ Job 在此期间结束并从公共快照消失
+ run.sh 因节点异常或磁盘满没有写入终态
+ 波形不完整
```

此时：

- SQLite 没有捕获到 Job 的结束状态；
- 最新公共快照已经没有该 Job；
- 状态文件仍为 Running 或缺失；
- 没有可用业务结果；
- `bhist` 又不适合作为自动查询来源。

系统不能诚实地判断它是仿真失败、节点故障、磁盘故障还是其他原因，只能标记“状态未知”。

IT 无法提供保留时间更长的历史任务数据。因此当前项目接受这个恢复边界：没有足够证据时保留“状态未知”，不继续尝试自动推断。

项目必须提供人工恢复能力：用户可以按 Run、Corner、Stage、算法调用序号、Testcase 状态等条件筛选全部 Case，检查最后一次状态证据，然后明确选择需要重新提交的 Case。

人工重新提交只为选中的 Testcase 创建新的执行尝试。旧尝试、旧 Batch 以及数据库中的状态历史会保留；新 Attempt 使用新的 Scratch 目录。回传时必须验证它仍是当前有效 Attempt，防止较晚结束的旧 Job 覆盖新结果。

## 8. 状态不一致时如何处理

推荐判断规则如下：

| 文件证据 | 最新公共快照及本地历史 | 输出证据 | 系统处理 |
|---|---|---|---|
| Submit | PEND | 无 | 等待排队 |
| Running | RUN | 可能有部分输出 | 继续等待 |
| Running 很久未变 | RUN | 可能有部分输出 | 仍视为运行；可以显示“长时间运行”提示 |
| Running 很久未变 | UNKNOWN 或连续快照状态异常 | 不完整 | 标记“状态待确认”，不能自动重提 |
| Running 很久未变 | EXIT | 不完整 | 标记仿真失败，等待用户决定忽略或重新仿真 |
| Running 很久未变 | DONE | 完整 | Status 没有 Complete，标记状态矛盾并等待用户决定 |
| Copyback Waiting | DONE 或已消失 | 不完整 | 仿真已成功但结果未回传；Recovery 提供重新复制和放弃旧 Submit 后重新运行两种操作 |
| 状态文件缺失 | PEND 或 RUN | 不完整 | 根据 LSF 状态继续等待 |
| 状态文件缺失 | EXIT | 不完整 | 标记仿真失败，等待用户决定 |
| 状态文件缺失 | DONE | 完整 | Status 证据缺失，标记状态矛盾并等待用户决定 |
| Complete | DONE | 任意 | 仿真成功，等待本组其他 Testcase；之后由 Postprocess 检查输出 |
| Complete | EXIT | 任意 | 仿真业务仍视为成功，同时显示 LSF 状态矛盾供用户检查 |
| Complete | 最新快照中已消失，但 SQLite 曾记录 DONE | 任意 | 仿真成功，继续等待本组推进条件 |
| 非 Complete | 最新快照中已消失，但 SQLite 曾记录 DONE | 完整 | Status 终态缺失，标记状态矛盾并等待用户决定 |
| 任意 | 最新快照中已消失，本地没有终态 | 完整 | 没有当前执行的 Complete，标记状态未知并等待用户决定 |
| 任意 | 最新快照中已消失，本地没有终态 | 不完整 | 标记“状态未知”，不能假装已经确认失败 |

“长时间”不能使用一个对所有仿真固定的短值。可以依据 Queue、Stage、仿真类型或历史运行时间设置超时提醒。

## 9. 建议增加两个异常状态

为了避免系统把不确定情况误判成失败并重复提交，建议增加：

### 状态待确认

表示已有证据互相矛盾，或者任务长时间显示 Running 但 LSF 暂时为 UNKNOWN。

此状态下：

- 不调用算法；
- 不自动重提；
- 安排下一次低频确认；
- 界面显示原因和最后检查时间。
- 用户可以通过 Case 筛选页面检查并决定是否人工重新提交。

### 任务丢失

表示经过 LSF 当前状态、历史状态和输出文件检查后，仍然找不到正在运行或已经完成的证据。

只有达到明确的确认条件后才能进入该状态。进入后仍然等待用户通过筛选页面选择忽略或重新仿真，不自动创建新的执行尝试。

对于因为公共快照历史已经消失而无法确认的情况，可以一直保留“状态未知”，然后由用户筛选和选择是否重新提交，不强制系统先自动改成“任务丢失”。

## 10. Array 结束后的完整处理顺序

```text
发现公共 bjobs.parquet 已更新
        ↓
一次查询全部未结束 Batch / Element
        ↓
将本次观察结果保存到 SQLite
        ↓
结合历史观察更新每个 Testcase 的执行状态
        ↓
结合 status.json、LSF 和输出文件整理每个 Testcase 的状态证据
        ↓
失败或不确定项：等待用户选择忽略或重新仿真
        ↓
重新仿真的项目创建新的执行记录和新 Batch，并再次等待
        ↓
重新判断当前 Stage、当前算法生成组是否还有未结束 Testcase
        ↓
当前组全部结束后触发一次批量 Postprocess
        ↓
Postprocess 生成 MT，并保存新增可用结果
        ↓
调用当前 Corner、当前 Stage 对应的算法
```

仿真状态和 Postprocess 状态必须分开。仿真成功但 Postprocess 失败时，当前 Corner 等待用户检查，不自动再次扫描。界面可以建议用户先重新执行 Postprocess；如果检查后确认源仿真有问题，用户仍可筛选对应 Testcase 重新仿真。Postprocess 自己会跳过已经处理的内容，因此用户重新执行时不要求 Workflow 精确维护待处理波形列表。

固定网络目录中的旧波形和 MT 不在重新提交前清理。新 Attempt 先回传到自己的隔离目录，只有当前有效 Attempt 才能由 Backend 发布为当前波形；Postprocess 随后更新对应 MT。因此算法不能通过“MT 文件存在”判断结果已经准备好，必须确认当前有效执行的仿真、结果发布与 Postprocess 都已完成。

## 11. Backend 重启后的恢复顺序

Backend 启动后：

1. 从 SQLite 读取所有未结束的 Batch 和 Element；
2. 读取已知状态文件和预期输出，不递归扫描无关目录；
3. 检查公共 `bjobs.parquet` 是否有新版本；
4. 有新版本时，一次查询所有仍未结束的 Job 并保存观察结果；
5. 按状态不一致判断表更新数据库；
6. 对已从快照消失又没有终态证据的任务标记“状态未知”；
7. 创建已经满足推进条件、但尚未执行的批量 Postprocess；
8. 将失败、状态待确认和状态未知的 Testcase 提供给人工筛选与决策页面；
9. 不对任何失败或不确定的 Testcase 自动执行 `bsub`。

恢复过程可以重复执行，不能重复创建 Postprocess、重试 Batch 或算法决定。

## 12. 当前建议的数据记录

每个 Testcase 执行尝试至少记录：

- Testcase ID 和第几次执行；
- Batch ID、LSF Job ID 和 Array Index；
- Backend 记录的提交时间；
- 状态文件中的开始、结束时间；
- 最后一次读取状态文件的时间和内容；
- 最后一次读取公共快照的时间、快照时间和观察结果；
- LSF 退出码和终止原因；
- SP、日志和波形路径；
- 输出文件观察结果；
- 仿真最终判断及判断依据；
- 用户是否已选择忽略或重新仿真；
- 当前有效的是哪一次执行。

这样界面可以明确显示：

```text
当前判断：状态待确认
文件状态：Running，最后更新于 10:32
LSF 快照状态：UNKNOWN，快照生成于 10:35，读取于 10:40
输出状态：波形不完整
下一步：5 分钟后再次检查，不自动重提
```

## 13. 留到代码设计时确认的内容

- 公共数据到底是 DuckDB 数据库还是由 DuckDB 读取的 `bjobs.parquet`；
- 快照生成时间、原子替换方式、字段和 DONE / EXIT 保留时间；
- Status 文件的最终字段和 Wrapper 错误码。

这些信息影响接入实现，但不改变当前业务规则：仿真成功只认当前执行的 `status_complete`；失败、不确定和 Postprocess 失败都等待用户处理，不自动重试。
