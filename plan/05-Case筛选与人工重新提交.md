# Case 筛选与人工重新提交

> 状态：讨论稿
>
> 目的：当 Testcase 失败或状态无法确认时，让用户能够从大量 Case 中准确筛选，并决定忽略还是重新仿真。

## 1. 为什么需要人工恢复入口

当前环境存在以下限制：

- 公共 `bjobs.parquet` 约每 5 分钟更新一次；
- 已完成 Job 一段时间后可能从公共快照中消失；
- `bhist` 查询速度很慢，不适合自动恢复；
- 状态文件与大型波形使用同一个文件系统，磁盘满时两者都可能写入失败；
- LSF 或执行节点异常可能让 `run.sh` 没有机会写入终态。

如果 Backend 关闭期间同时发生这些情况，系统可能只能得到：

```text
SQLite：最后记录为 Running
公共快照：已经找不到 Job
状态文件：Running 或缺失
波形：缺失或不完整
```

此时系统不能可靠判断任务是否还会继续、为何结束或是否适合自动重提。

当前确定的处理方式是：

```text
标记为“状态未知”
        ↓
不自动重新提交
        ↓
用户通过 Case 列表筛选
        ↓
用户明确选择忽略或重新仿真的 Case
```

## 2. 页面中一行表示什么

筛选和重新提交的主要操作单位应当是 Testcase，而不是整个 Run、整个 Corner 或整个旧 Array。

每一行显示一个 Testcase 及其当前有效执行情况：

```text
Testcase
├── Run
├── Corner
├── Stage
├── 算法调用序号（UI 可显示为轮次）
├── Code / Mode 摘要
├── 当前结果状态
└── 最近一次执行尝试
    ├── Batch / LSF Job ID / Array Index
    ├── status.json 最后状态
    ├── 公共快照最后状态
    ├── 波形检查结果
    ├── Postprocess 状态
    └── 最后更新时间
```

用户可以展开一行查看该 Testcase 的全部历史执行尝试，但批量操作默认针对 Testcase 当前需要解决的状态。

## 3. 建议支持的筛选条件

### 业务范围

- 当前 Run；
- PVT 条件；
- Corner；
- Stage；
- 算法调用序号（UI 可显示为轮次）；
- 算法名称。

### Testcase 与执行状态

- 尚未提交；
- 等待 LSF；
- 运行中；
- 状态待确认；
- 状态未知；
- 仿真失败；
- 仿真成功；
- 仿真已完成、结果等待复制；
- Postprocess 等待中；
- Postprocess 失败；
- 结果完整；
- 已被后续执行替代；
- 已取消。

### LSF 与文件证据

- 最后一次公共快照状态；
- 是否已从公共快照消失；
- 状态文件状态；
- 状态文件是否缺失；
- 状态文件最后更新时间；
- 波形是否存在；
- MT 是否存在；
- 最后一次执行时间范围；
- 重试次数；
- Batch ID、LSF Job ID 和 Array Index。

至少要支持组合筛选，例如：

```text
Run = R100
Stage = 1
Corner = 某一组 Corner
状态 = 状态未知
波形 = 缺失
最后更新时间早于 24 小时前
```

Case 列表不跨多个 Run 搜索。用户先进入一个 Run，再在该 Run 内组合筛选。

Corner 需要支持紧凑列表输入，例如：

```text
1,2,3-5,6-20
```

同时支持反向排除：用户可以表示“选择当前 Run 的全部 Corner，但排除这一组编号”。输入解析后，界面要先展示实际匹配数量和部分预览，避免范围或排除方向写错后直接批量提交。

## 4. 大量数据下的选择方式

一次 Run 可能有数万到十万个 Testcase，不能把全部记录一次加载到前端。

筛选、排序和分页由 Backend 基于 SQLite 完成。界面每次只显示一页结果。

需要区分两种选择方式：

### 选择当前页面中的 Case

用户逐条勾选当前页可见的 Testcase。

### 选择全部符合筛选条件的 Case

用户可以选择：

> 选择符合当前筛选条件的全部 12,438 个 Testcase

此时不能只保存当前页的 ID。Backend 需要保存或重新执行完整筛选条件，并允许用户排除少量不想处理的 Testcase。

重新提交前必须重新计算一次匹配数量和状态，防止用户打开页面后某些 Testcase 已经恢复成功。

## 5. 重新提交前的预览

用户点击“重新提交所选 Case”后，系统先生成预览，不立即执行 `bsub`。

预览至少显示：

```text
选中 Testcase 总数
├── 状态未知数量
├── 已确认失败数量
├── 已经完成的数量
├── 仍可能在 LSF 中运行的数量
├── 可能覆盖或混合既有输出的数量
└── 即将生成的 Array Batch 数量
```

并按实际提交规则显示分组：

```text
Corner A / Stage 1 / 算法调用 #2 → 新 Array，包含 7 项
Corner B / Stage 2 / 算法调用 #1 → 新 Array，包含 3 项
Corner C / Stage 1 / 算法调用 #4 → 新 Array，包含 12 项
```

不同 Corner 不混入同一个 Array。不同 Stage、算法调用生成组或运行配置不兼容的 Testcase 也不能强行放进同一个 Array。

## 6. 用户可以决定忽略或重新仿真

对于失败、状态未知或 Postprocess 无法取得有效结果的 Testcase，系统统一等待用户决定，不设置自动重试次数。

选择“忽略”表示这个 Testcase 不再阻塞当前算法生成组。系统保留它的失败和忽略记录，Postprocess 与算法只使用剩余的有效结果。如果算法认为剩余数据仍然不足，它可以正常提出新的 Testcase；系统不能自行拿缺失结果补数。

选择“重新仿真”则按下述规则创建新的执行记录和新 Batch。

### 重新仿真与复制恢复规则

### 已确认失败

允许正常重新提交。

### 状态未知或状态待确认

允许用户重新提交，但必须明确提示：

> 旧任务缺少可靠终态，仍存在它尚在运行或稍后产生结果的可能。继续操作可能造成重复仿真。

用户确认后才创建新执行。

### 已经成功并且结果完整

允许重新提交。Status 筛选的目的之一就是让用户能够筛出已经完成的 Case，并决定是否再次运行。

界面需要提示重新运行可能覆盖或改变固定目录中的既有波形和 MT，但不替用户禁止操作。

### 仅 Postprocess 失败

当前 Corner 等待用户检查，不自动再次扫描。界面可以优先建议只重新执行 Postprocess；用户也可以在确认源仿真有问题后，明确选择相应 Testcase 重新提交仿真。

### 仿真完成但结果等待复制

界面同时提供“重新复制”和“放弃本次 Submit 并重新运行”。重新复制根据 LSF 子任务创建的 hostname 标记，通过普通 SSH 登录原节点，把 Scratch 文件夹全部内容复制到 Testcase 所在磁盘的 Attempt 回传目录。Backend 明确显示源目录不存在、SSH 失败或目标仍不可写等错误，由用户决定继续复制还是放弃旧 Submit 并重新提交。

选择“放弃本次 Submit 并重新运行”时，必须先把旧 Attempt 标记为 `abandoned`/已被替代并保留其错误、hostname 标记和历史记录，再创建新的 Attempt 和 Batch。该操作必须经过预览确认，不能把复制按钮的失败自动转换成重新提交。

### 当前明确仍在 PEND 或 RUN

允许重新提交，但必须强提示可能造成重复计算和旧 Attempt 晚完成。各 Attempt 使用独立 Scratch 和回传目录，Backend 不允许旧结果覆盖当前结果。

系统不根据 Status 自动排除用户已经明确选择的 Case。Status 是筛选和风险判断依据，不是提交权限。

## 7. 重新提交如何创建数据

人工重新提交不创建新的 Testcase 或新的 Case 目录。它只为同一个 Testcase 创建新的数据库执行记录，并通过新 Batch 再次引用原固定目录。

```text
Testcase
├── 执行尝试 #1
│   ├── 最后状态：状态未知
│   ├── 旧 Batch / Job ID / Index
│   └── SQLite 中的旧执行历史保留
│
└── 执行尝试 #2
    ├── 原因：用户人工重新提交
    ├── 创建时间
    ├── 引用原 Case 网络目录和 SP
    ├── 使用新的 Scratch 和 Attempt 回传目录
    ├── 新 Batch / Job ID / Index
    └── Backend 核对身份后发布本次结果
```

Backend 根据选中的 Testcase 重新分组并创建新 Batch。每个新 Batch 仍使用自己的不可修改任务清单。

人工重新提交不单独弹出一套复杂的 Queue / 资源编辑表单。每次创建新 Batch 时，统一读取 Setting 中当时有效的 LSF 配置，并把实际使用的配置副本保存在 Batch 记录中。因此用户如果要改变 Queue 或资源参数，先修改 Setting，再执行本次提交即可；旧 Batch 的配置记录不随 Setting 变化。

新 Batch 清单引用 Case 的固定网络输入/结果目录，并为新 Attempt 使用独立 Scratch 和回传目录。stage-in 只复制本次最终 SP。

如果状态未知的旧 Job 实际仍在运行，两个执行会写入各自 Scratch 和 Attempt 回传目录。系统仍会在预览中提示资源重复消耗和旧任务晚完成风险，但旧 Attempt 不允许直接覆盖当前结果。

重新提交前不删除已有波形、MT 或其他仿真结果：

- 新仿真先回传到 Attempt 专属目录，Backend 只发布当前有效 Attempt 的波形；
- 本次批量 Postprocess 负责覆盖旧 MT；
- Backend 在提交前把 Status 更新为包含新执行编号的 Submit；
- Status 无法正常更新时，不提交该 Case。

旧 MT 在新任务运行期间仍然存在。界面可以显示它是历史文件，但 Workflow 和算法不能把它当作本次执行已经完成的证据。

系统需要记录本次人工操作：

- 操作时间；
- 使用的筛选条件；
- 实际选中的 Testcase 数量和 ID；
- 用户确认时各 Testcase 的最新状态；
- 用户确认的风险提示；
- 重新分组后创建的 Batch；
- 可选的用户备注。

## 8. 防止重复点击和重复创建 Batch

用户确认后，Backend 需要先在一个数据库事务中：

1. 再次检查 Testcase 当前状态；
2. 显示并记录与预览相比已经变化的状态；
3. 为用户最终确认的 Testcase 创建新的执行尝试；
4. 创建人工重新提交操作记录；
5. 为后续 Batch 分配唯一标识。

同一个人工操作请求需要有唯一 ID。即使用户重复点击、界面超时重试或 Backend 重启，也不能为同一批 Testcase 重复创建多组新执行。

## 9. 旧任务后来完成时如何处理

状态未知的旧任务可能在人工重提后仍然继续运行：

```text
执行尝试 #1：后来发现成功
执行尝试 #2：人工重提后也成功
```

两次执行分别使用独立 Scratch 和 Attempt 回传目录，因此原始回传结果不能互相覆盖。Backend 只把当前有效 Attempt 发布到 Postprocess 能识别的位置。

系统保留两次提交的数据库记录、Batch、Job ID、Index、hostname 和观察到的状态。Attempt 回传目录的长期保留仍取决于网络结果盘清理策略。

每次 Status 写入都携带执行编号。Backend 只接受与当前执行记录匹配的 Status；旧 Job 即使后来成功，也只进入自己的 Attempt 回传目录，不发布为当前结果。

这是用户对状态未知、运行中或已完成 Case 执行重新提交时接受的行为。预览必须显示风险，但系统不阻止操作。

## 10. 用户视角的完整流程

```text
用户打开 Case 列表
        ↓
进入一个 Run，按 Corner / Stage / 算法调用序号 / 状态筛选
        ↓
查看状态文件、公共快照和输出证据
        ↓
选择当前页或全部匹配 Case
        ↓
点击“重新提交所选 Case”
        ↓
系统重新检查状态并生成预览
        ↓
用户确认重复仿真风险
        ↓
为选中 Testcase 创建新的执行尝试
        ↓
按 Corner / Stage / 算法调用生成组重新组成 Array Batch
        ↓
提交 LSF
        ↓
保留旧执行历史，继续正常跟踪
```

## 11. 留到界面设计时确认的内容

- Corner 编号的完整语法、非法输入提示和反向排除的具体写法；
- 是否需要导出当前筛选结果，供用户离线检查。
