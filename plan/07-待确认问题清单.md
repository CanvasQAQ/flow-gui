## 本轮已经形成的设计

- 追加扫描会加入新 Corner，并重新解析所有以前有问题的 Corner；正常 Corner 不覆盖；
- 覆盖扫描会重新解析当前目录中的全部 Corner；未找到的旧 Corner 标记为文件缺失，不删除历史；
- Run 创建后仍可继续补充 Corner；
- 一个 Corner 加入 Run 时固定自己使用的原始输入版本，防止运行过程中静默换 SP；
- 新扫描到的 Corner 由用户明确选择后补充进某个已有 Run，不自动提交；
- Rollback 是后端调试能力，不暴露到前端 GUI；
- Rollback 可以按 Run 和 Corner 列表或范围批量执行；
- 每个 Corner 回到指定 Stage 的算法决策之前，复用此前完成的仿真、MT 和 Loss，再用当前算法代码重新决策；
- 受影响路径中仍有活动 Job 时，跳过该 Corner，等待用户手动处理；
- 旧决策和后续路径保留但标记为已被替代，不删除历史文件；
- 不为调试更新建立算法版本管理；
- 当前不单独设计 Replay，所需能力统一放入 Rollback。
- LSF Runner 只把单个最终 SP stage-in 到计算节点 `/SCRATCH`；该 SP 可以独立运行；
- `/SCRATCH` 内容约 24 小时后由站点清理；项目不管理或识别该机制；
- 只有实际运行的 LSF 子任务负责取得 hostname，并在 Case 网络目录创建同名零字节恢复标记；
- stage-out 复制 Scratch 文件夹中的全部内容；
- copy-back 失败时，Recovery 同时提供重新复制和放弃旧 Submit 后重新运行；Backend 只明确返回操作错误，不替用户判断 Scratch 是否已清理。

以上规则的完整说明见《重新扫描、补充 Corner 与 Rollback》。如果 Review 时发现不符合实际，再把具体问题重新加入本清单。

## Backend 第一版参考实现的处理方式

为了让开发机可以先完成工程搭建，上述未决项已经全部放到 Adapter 或 Site
Config 后面，并提供可替换的参考实现：

- 算法使用 Python factory + 动态 Stage/Decision 契约；
- Batch 默认使用不可修改的 JSON Manifest，Index 从 1 开始；
- SP 使用 HSPICE `.PARAM` 精确替换，MT 使用传统空格 Measure 表格 Parser；
- 公共快照列名完全由配置映射，DuckDB 一次筛选全部活动 Job；
- 仿真、LSF、Postprocess 的命令均使用参数数组，不经过 shell 字符串；
- 文件名、Queue、资源、Postprocess 命令和并发数均保留为现场配置；
- 真实提交默认关闭，必须在真实机器通过 dry-run 验收后开启。

这些是工程默认值，不等于现场格式已经确认。如果真实数据不符合参考格式，优先
替换对应 Adapter，不修改 Workflow 核心状态机。
