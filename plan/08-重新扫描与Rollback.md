# 重新扫描、补充 Corner 与 Rollback

> 状态：讨论稿
>
> 目的：说明创建 Run 后如何继续补充 Corner，以及算法代码更新后，如何让单个 Corner 回到某个历史决策点重新向后推进，而不重复已有仿真。

## 1. 基础 Corner 清单和 Run 中的 Corner 是两层数据

为了同时满足“基础目录可以继续补充”和“运行中的 Corner 不能突然换输入”，需要把两层数据分开：

```text
基础 Corner 清单
├── 当前扫描到的 SP / MT
├── 当前解析出的初始 Code
├── 是否可用
└── 输入版本

Run
├── 固定的 PVT 条件和算法方案
└── 分批加入的 Run Corner
    ├── 加入 Run 的时间
    ├── 加入时采用的基础 Corner 输入版本
    ├── 原始 SP 和初始 Code 的固定记录
    └── 自己独立的 Stage 流程
```

Run 创建后，Corner 集合不是永久封闭的。用户可以刷新基础目录，再把新出现或修复成功的 Corner 补充到已经存在的 Run。

但一个 Corner 一旦加入 Run，它在该 Run 内使用的原始 SP 和初始 Code 就固定下来。以后覆盖扫描不会让这个已经运行过的 Corner 在用户不知情时换用新输入。

这样可以避免同一 Corner 前几轮使用旧 SP、后几轮突然使用新 SP，导致 Code 和 Loss 无法直接比较。

这里的“输入版本”不能只是数据库中的一个编号或原文件路径。基础目录中的文件以后可能被覆盖，因此系统需要为每个成功扫描的版本保留一份不可修改的输入快照，至少包括：

- 原始 SP 的实际内容；
- 解析得到的初始 Code；
- 原始 MT 的实际内容或不可修改副本、必要的解析结果和文件指纹；
- 扫描时间。

多个 Run 使用同一个 Corner 输入版本时可以共同引用这一份快照，不需要为每个 Run 重复复制。只有覆盖扫描确认内容发生变化时，才建立新的输入版本。

## 2. 追加扫描

“追加扫描”用于补充数据，不改动已经正常的基础 Corner。

扫描时处理：

- 新发现的 Corner：解析 SP、MT 和初始 Code，成功后加入基础 Corner 清单；
- 以前解析失败或文件不完整的 Corner：重新解析，成功后从“不可用”恢复为“可用”；
- 仍然有问题的 Corner：更新错误原因和检查时间，继续保持不可用；
- 已经正常的 Corner：保持原记录，不因为文件时间变化而覆盖；
- 本次没有扫描到的旧 Corner：保持原记录，不标记删除或缺失。

追加扫描完成后显示汇总：

```text
新增 Corner 数量
恢复可用的 Corner 数量
仍然异常的 Corner 数量
没有改动的正常 Corner 数量
```

## 3. 覆盖扫描

“覆盖扫描”可以理解为对基础 Corner 清单做一次完整刷新。

推荐规则：

- 对本次扫描到的全部 Corner 重新解析，不论以前是否正常；
- 新 Corner 正常加入；
- 已存在 Corner 如果内容发生变化，则建立新的不可修改输入版本，并把它设为基础清单的当前版本；
- 解析失败的 Corner 标记为不可用，并保留具体错误；
- 以前存在、但本次完全没有扫描到的 Corner 不物理删除，而是标记为“当前文件缺失、不可用于新增运行”；
- 保留旧版本编号和扫描记录，便于解释历史 Run 使用过什么。

不直接删除旧 Corner，是因为历史 Run、Testcase 和结果仍可能引用它。这里的“覆盖”表示更新当前可用版本，不表示清除历史。

## 4. 扫描不会自动改变已有 Run

无论追加还是覆盖，扫描只更新基础 Corner 清单，不直接创建仿真任务，也不自动把所有新 Corner 塞进每个 Run。

用户进入某个 Run 后，通过 Corner 列表或反向排除条件选择要补充的 Corner。系统先预览：

- 哪些 Corner 是这个 Run 中尚未存在的新 Corner；
- 哪些已经在 Run 中，不能重复加入；
- 哪些当前不可用；
- 实际将新增多少个 Corner。

用户确认后，系统才把新 Corner 加入该 Run，并使用该 Run 已有的 PVT 条件和算法方案，从第一个 Stage 独立开始推进。其他 Corner 不暂停，也不重新计算。

一个 Run 可以在不同时间分多次补充 Corner。每次补充操作都保存选择条件、实际加入的 Corner 和输入版本。

## 5. 已在 Run 中的 Corner 遇到基础输入更新

覆盖扫描可能发现某个 Corner 的 SP、MT 或初始 Code 已经变化。

如果这个 Corner 还没有加入某个 Run，之后加入时直接使用最新版本。

如果它已经在 Run 中：

- 当前流程继续使用加入 Run 时固定的输入版本；
- 界面提示“基础 Corner 已有新版本”；
- 不自动重建 SP，不自动废弃已有 Loss，也不自动触发 Rollback；
- 如果用户确实要在这个 Run 中使用新版原始输入，需要执行一次明确的“按新版输入重新开始此 Corner”操作。

“按新版输入重新开始”与普通 Rollback 不同：原始输入已经改变，旧仿真结果不能继续复用。它会保留旧历史，但为这个 Corner 创建一条使用新版输入的新流程，并从第一个 Stage 开始。

## 6. Rollback 是后端调试能力

Rollback 用于算法调试，不作为普通用户功能，也不需要在前端 GUI 中提供按钮或页面。

它支持一次选择一个或多个 Corner。后端入口至少接收：

- Run；
- Corner 列表或范围，例如 `1,2,3-5,6-20`，也可以反向排除；
- 要回到的 Stage 决策点。

对每个 Corner，目标是当前有效路径中指定 Stage 完成后的算法决定。例如回到 Stage 2 的决策点，表示继续保留 Stage 2 已完成的仿真、MT 和 Loss，只撤销“Stage 2 下一步怎么走”这个决定及其后续路径。

```text
一批 Corner 的 Stage 2 仿真和 Postprocess 已完成
        ↓
旧算法决定它们进入 Stage 3
        ↓
调试并更新算法代码
        ↓
后端批量 Rollback 到 Stage 2 决策点
        ↓
复用每个 Corner 自己已有的 Stage 2 数据
        ↓
使用当前算法代码分别重新决策
```

Rollback 不重新运行目标决策点以前已经成功完成的仿真，也不重新执行已经成功的 Postprocess。

## 7. 批量 Rollback 的检查结果

因为各 Corner 独立推进，同一次批量操作中可能出现不同情况。后端先给出检查结果：

```text
可以 Rollback
尚未到达目标 Stage
目标 Stage 还没有完成决策
后续仍有 PEND / RUNNING Job
后续存在状态待确认或状态未知 Job
已经停在该决策点，没有需要撤销的后续路径
```

批量执行时只处理满足条件的 Corner，其他 Corner 跳过并返回具体原因。再次执行同一操作不能重复创建多条相同的新路径。

这份结果只需要由后端调试入口返回并记录日志，不需要设计前端展示页面。

## 8. Rollback 前必须手动处理运行中的任务

某个 Corner 的被撤销路径中如果仍有尚未结束的 Job，该 Corner 不能执行 Rollback。

用户先手动处理这些任务，例如：

- 等待它们结束；
- 在 LSF 中删除等待任务或终止运行任务；
- 对状态未知的任务完成必要检查和确认。

Rollback 操作本身不执行批量 `bkill`。用户处理后再次运行后端检查或 Rollback；仍存在可能继续写入旧 Case 目录的任务时，该 Corner 继续保持阻塞。

## 9. Rollback 实际改变什么

对每个可以处理的 Corner，系统执行：

1. 保留目标决策点以前的 Testcase、仿真结果、MT 和 Loss；
2. 将原算法决定标记为“已被 Rollback 替代”；
3. 将该决定之后创建的 Stage、Testcase 和 Batch 标记为旧路径，不再推动当前流程；
4. 不删除旧路径数据库记录，也不删除旧文件；
5. 读取目标决策当时可用的算法输入；
6. 直接使用当前后端中的算法代码重新计算；
7. 保存新的算法决定；
8. 根据新决定补充当前 Stage 的 Testcase，或进入算法指定的新 Stage。

不为这项调试能力建立算法版本管理。用户自行确定何时更新了算法代码，以及哪些 Corner 需要 Rollback。

如果当前算法判断目标 Stage 的数据仍然不够，该 Stage 执行重新变为进行中，并在原 Stage 执行目录中增加新的、名称不重复的 Testcase。如果算法决定进入下一 Stage，则建立一条新的下游 Stage 执行记录。

## 10. Stage 文件夹需要区分多次执行

Rollback 后可能再次进入一个历史上已经运行过的 Stage。为了避免新旧 Testcase 使用同一目录，需要给每次 Stage 执行一个独立编号。

目录可以采用类似形式：

```text
corner_0001/
├── stage_2__001/
│   ├── testcase_a/
│   └── testcase_b/
├── stage_3__001/          # Rollback 前的旧分支
│   └── ...
└── stage_3__002/          # 新算法决定后再次进入 Stage 3
    └── ...
```

界面仍然显示“Stage 2”“Stage 3”，执行编号主要用于区分历史路径和固定目录。

每个 Stage 执行文件夹中仍然直接包含算法命名的 Testcase 子文件夹，Postprocess 只扫描当前有效的 Stage 执行目录。

如果 Rollback 后算法决定继续在当前 Stage 补充 Code，则继续使用当前 Stage 执行目录。算法仍需保证新 Testcase 名称在这个目录内不重复。

## 11. 不单独设计 Replay

当前业务需要的是“回到历史算法决策点，复用已有仿真结果，用更新后的算法重新向后推进”。这个能力统一命名为 Rollback。

第一版不再单独设计 Replay 按钮或 Replay 状态，避免出现两个含义相近但行为不清楚的操作。
